# Decisions

Assumptions made where the docs were ambiguous. Newest last.

| # | Decision | Reason |
|---|---|---|
| D1 | Tailwind CSS v4 (CSS-first tokens in `app/globals.css`) with hand-written shadcn-style components on Radix primitives. | Current default for Next 15; no config file drift; tokens map 1:1 to docs/06. |
| D2 | Zod 3 + `@hookform/resolvers` 3. | Resolvers 6 has an unresolved peer conflict at install time; v3 is stable. |
| D3 | Session = Firebase **session cookie** (httpOnly, 5 days) minted by `POST /api/auth/session` from a fresh ID token (<5 min old). Server layouts verify it with `checkRevoked=true`, so disabling a user locks them out. | Needed for server-side route guards; middleware cannot run firebase-admin. |
| D4 | `middleware.ts` only reads the role from the cookie payload (unverified) for redirects. Real checks: `requireRole()` in layouts and Firestore/Storage rules. | Edge-safe UX routing; never a security boundary. |
| D5 | Stale/invalid cookie redirects to `/logout` (clears cookie) instead of `/login`. | Prevents a redirect loop with the middleware. |
| D6 | Phase 0 rules are deny-all; each phase opens only what it needs and adds emulator tests. | Least privilege. |
| D7 | Nav lists only routes that exist; each phase appends to `components/shell/nav-config.ts`. | No dead links. |
| D8 | Rules tests live in `tests/rules` and run with `npm run test:rules` (needs Java for the Firestore emulator). Unit tests run with `npm test`. | Separate fast and emulator suites. |
| D9 | Day boundaries use fixed UTC+5 (Pakistan has no DST) in `lib/time.ts`; Firestore rule uses the same arithmetic. | Matches docs/03 journal-lock rule. |
| D10 | UI re-based on the ui-ux-pro-max skill: palette/type in design-system/traxio/MASTER.md, contrast enforced by lib/design/contrast.test.ts. Search script not run (no Python); CSV data read directly. | User request; fixes AA failures found in the Phase 0 UI. |
| D11 | Dark mode stays opt-in/system-follow (skill flags dark-by-default as an anti-pattern for general SaaS), but is designed in parallel with light. | Skill ui-reasoning rule. |
| D12 | Employee Auth email is always username@traxio.app; a real email is stored separately as contactEmail. | Lets username login work without a pre-login lookup (rules deny anonymous reads). Only the admin signs in with a real email. |
| D13 | users documents are created/changed only by server routes (Admin SDK). The only client write is the admin setting photoUrl. Businesses are written by the admin client directly under rules. | Keeps roles, claims and status tamper-proof; businesses need no server logic. |
| D14 | Disabling an employee disables the Auth user, revokes refresh tokens and flips status. Server pages reject them immediately (session cookie is verified with revocation); an already-issued ID token can still read Firestore for up to 1 hour. | Avoids an extra Firestore read on every rules check; acceptable for an internal team tool. |
| D15 | Business colours are a curated swatch id (indigo, iolet, …) mapped to --biz-* CSS tokens, not free hex. | Guarantees contrast in both themes. |
| D16 | All task, routine, audit and activity writes happen in server routes inside one Firestore transaction via lib/server/task-store.ts (commitTaskPlan). Clients only read; rules deny every client write on these collections. | One shared writer guarantees task + audit + activity are atomic and nothing changes without a trail. |
| D17 | Workflow rules live in pure functions (lib/domain/tasks.ts): transition table, sub-task gate, review flow (an employee finishing a review-required task lands in Under Review; only the admin approves), blocked needs a 3-300 char reason. The server planners and the UI both use them. | Testable without Firebase; one source of truth. |
| D18 | Daily instance id is ${templateId}__; generation checks existence and uses create (never overwrite), falling back to one-by-one on a race. Cron (00:05 PKT, ercel.json) and a lazy call from the employee dashboard share the same function. | Idempotent under overlap; Hobby-plan friendly (once a day). Holidays/leave are added in Phase 6. |
| D19 | A routine edit rewrites today's copy only while it is untouched (To-Do, no steps ticked); earlier days are never changed. Deleting or pausing a routine keeps existing days. | Matches 'edits apply from today onward, never rewrite history'. |
| D20 | Employee Today shows today's tasks plus unfinished one-off tasks from earlier days ('Carried over'). Missed daily routines are not carried over. | Avoids a growing pile of stale routine copies; escalation (Phase 8) covers lateness. |
| D21 | Task attachments live at 	asks/{taskId}/… (admin upload, assignees read via a Firestore lookup in the Storage rule). They are shared as download URLs, so anyone holding a link can open the file. | Simple links for employees; acceptable for internal documents. |
| D22 | UI default is the light, soft-gradient look from the login page (the user's preference). Dark mode stays available through the theme toggle but no longer follows the system setting. | Direct user feedback. |
| D23 | Several assignees: each has their own tick; mode ll completes when everyone has finished, ny when the first does. An employee reopening clears only their own tick; the admin resets everyone; sending a review task back resets everyone. All assignees of one task must be in the same business. | Keeps business filters, colours and audit unambiguous. |
| D24 | Dependencies and related links connect one-off tasks only. The rule is enforced from live statuses inside the transaction; waitingOnIds, linkTitles and ssigneeNames are display copies kept in sync by the shared writer (cascade on completion, rename and delete). Dependency loops are rejected by a graph walk before saving. | Employees can't read tasks they aren't on, so names must travel with the task; daily copies are routine-owned and would drift. |
| D25 | Board shows the chosen period (Today / This week / Last 7 / Last 30 days) plus unfinished one-off tasks from earlier days. Dragging resolves through the same move rules as the menu (vailableMoves). Keyboard users jump column to column with the arrow keys. | One source of truth for what a move does; accessible by default. |
| D26 | The tags filter from docs/02 is deferred: tasks have a 	ags field but no way to create tags yet, so a filter would be empty. It lands with custom fields in the post-launch wave. | Don't ship a control with nothing behind it. |
| D27 | Local demo mode uses the Firebase emulators and a seed script that refuses to run unless the Admin SDK points at them. Demo logins live in scripts/seed-emulator.ts. | Lets the app be tried and tested before a real Firebase project exists, with no risk to production data. |
| D28 | Reminders, questions and chat messages are written by server routes; browsers only read. Exceptions under rules: a recipient stamps their own reminder read receipt with the server time, and your own typing marker in a chat you can use. | Keeps authorship, unread counters and statuses consistent and tamper-proof. |
| D29 | Chat in v1 is direct (admin and one employee) plus Everyone. Per-business groups and the online dot are deferred (the dot arrives with presence in Phase 6). Chat access is decided by chat id (everyone or dm_<uid>), with no membership lists to maintain. | Matches the single-admin model; avoids stale membership. |
| D30 | Files: reminders upload to reminders/<id>, chat to chats/<chatId>, question threads to the employee's private folder u/<employeeId>/q (only they and the admin can read it). The server checks attachments sit in the expected folder. | Nobody can attach a file from someone else's private folder. |
| D31 | The WhatsApp copy option on reminders waits for Phase 8 with the rest of WhatsApp. Closed questions stay closed until the admin reopens them. | Don't ship a control with nothing behind it. |
| D32 | A journal is one document per employee per PKT day. The rules compute today's date from the server clock and require the document id to contain it, so only today's journal can ever be written; the body fields (date, dayIndex, employeeId) are checked too. A device clock that is wrong or a midnight rollover gives a clear save error instead of silent loss. | Makes the lock independent of anything the browser sends. |
| D33 | Only the employee writes their journal (the admin reads). Edits autosave after 0.8 s with merge writes of just the changed hour, and flush on blur and when leaving the page. | Fast, and the admin can't put words in an employee's mouth. |
| D34 | The :55 prompt minute is a constant for now; it becomes configurable with the Automation settings in Phase 8. Fill rate counts an hour as logged when it has text or a task, over the person's working hours (their own or the business's) on working days only. | Matches docs/02 without a settings screen that does nothing yet. |
| D35 | Leave requests may start up to 7 days in the past (sick days are often logged afterwards) and last up to 60 days. Only whole-day leave pauses daily tasks; a short excuse never does. | Matches how teams actually ask for time off. |
| D36 | A holiday applies to every business; a closure applies to one. The calendar id is date plus scope so a date can only exist once. Fixed national days can be added in one click; moon-based holidays are added by hand. | No duplicates and no wrong guesses about Eid dates. |
| D37 | The admin sees "Offline" when a heartbeat is older than 3 minutes, even if the browser never said goodbye. | A closed laptop shouldn't look online. |
| D38 | The audit page loads a time range newest-first in pages of 300 and filters, searches and exports what is loaded; "Load older entries" widens it. Filtering is client-side so no extra indexes are needed. | Keeps reads and indexes small for one admin. Export says how many rows it holds. |
| D39 | CSV cells that start with = + - @ get a leading apostrophe, and the file has a BOM and CRLF. | A task title can't turn into a spreadsheet formula, and Excel reads it as UTF-8. |
| D40 | The admin's notifications live in one shared "admin" mailbox (like the admin unread key in chat), not under a user id. Employees' use their uid. Rules let each side read only its own and only mark read. | There is exactly one admin, so no lookup is needed and a second admin account later sees the same bell. |
| D41 | A notification is written inside the transaction of the change that caused it, and the browser push is sent after commit. A failed or retried attempt sends nothing. | The bell can never disagree with the data, and push failures never undo a change. |
| D42 | An escalation level's flag is set before the alert is sent. A failed send is logged and not retried. If the person is on leave or the day is a holiday, no flag is set, so it can still fire later. | At most one alert per level, even when two runs overlap. Missing one alert beats sending duplicates. |
| D43 | Escalation only covers To-Do and In Progress tasks due within the last 48 hours. | Blocked and in-review tasks already have an owner, and old abandoned tasks shouldn't alert forever. |
| D44 | The second alert always reaches the admin in the app and also on WhatsApp when an admin number is set. | The alert is never lost just because WhatsApp isn't configured. |
| D45 | The briefing is claimed per person per day (automationRuns document), so overlapping runs send it once. Employees without a number are skipped. | Idempotent without a scheduler guarantee. |
| D46 | Task assignment does not notify yet. The task writer is a separate port, and the bell already covers reminders, replies, leave and alerts. | Smaller, safer change. Easy to add as a follow-up. |
| D47 | "Late" in analytics means finished after the due time, or still open past it. Open tasks not yet due and tasks with no due time count as neither, so an early-week view isn't dragged down by work that isn't late. | Reads as "how often are we late", not "how much is unfinished". |
| D48 | A day with no tasks plots as a gap, not 0%. The trend goes weekly past 31 days. | A Sunday with no work isn't a bad day. |
| D49 | Journal fill counts only working days that have started, skipping holidays and closures, over each person's own working hours. Blocked reasons come from the audit trail, not the current blocked list. | History is accurate even after tasks move on. |
| D50 | Changing the analytics period remounts the page (skeleton, then fresh numbers) instead of keeping the old frame. | Numbers from two periods must never appear under one label. |
| D51 | The AI sees figures only: totals, per-person and per-business numbers and clipped blocked-reason text. Journal text is never sent, only how much of each journal was filled in. The prompt forbids inventing facts. | Privacy first, and nothing in the summary can't be traced to a figure. |
| D52 | Claude is called through the official SDK with the default model claude-opus-5-5 at low effort (thinking can't be turned off on it). Gemini goes over REST with the key in a header. With no key a rule-based template writes the same layout. An explicit AI_PROVIDER without its key is an error, never a silent fallback. | Works out of the box, costs nothing until a key is set, and a typo can't quietly change the provider. |
| D53 | The weekly job runs inside the Monday 9:00 morning job because Vercel Hobby allows two cron entries. It claims the week first (so overlapping runs write one summary) and releases the claim if it fails. A manual "week so far" is stored under its own id. | Idempotent and retryable. The in-progress week never blocks the finished one. |
| D54 | Traxio is text only: no Firebase Storage, so no file attachments (tasks, reminders, questions, chat, leave), no profile photos and no business logos. People show as coloured initials. Chat and replies need text. | Keeps the whole project on Firebase's free Spark plan (Storage is the one service that needs Blaze). Files can return later through a free third-party store if wanted. |
| D55 | WhatsApp is click-to-chat, not an API. Buttons open `https://wa.me/<number>?text=<message>` (app or WhatsApp Web) with the message typed in; the admin presses send. No Meta account, token, templates, per-message cost or send logs. The 9:00 AM briefing and late-task alerts became bell notifications (plus browser push), and the weekly summary has a "Share on WhatsApp" button. This replaces D45's WhatsApp briefing and the earlier automated sending. | Free, nothing to approve, and it keeps working for every workspace. The cost is that a person has to press send, and Traxio can't know whether the message went. |
| D56 | Multi-tenant by path: everything a workspace owns lives under `orgs/{orgId}/…`, not in shared collections with an orgId field. Rules wrap all existing rules in `match /orgs/{orgId}` and `isAdmin()/isEmployee()` now also require the token's `orgId` claim to equal that path. | The tenant boundary is the path itself, so a forgotten filter fails (empty or denied) instead of leaking, and existing rule bodies stayed almost unchanged. |
| D57 | Server code uses `scopeDb(db, orgId)` (prefixes every path) and a workspace id taken only from the verified session; browser code uses `orgCollection/orgDocument/orgRtdbRef` set from the same session. The communication/time-off services, whose ports use plain paths like `tasks/x`, needed no change. | A workspace-scoped database can't be pointed at another workspace by accident. |
| D58 | Sign-up is Google only for owners. The first sign-in has no workspace claim, so the login page asks for a workspace name (and optionally a code), then `POST /api/auth/workspace` creates `orgs/{id}`, the code reservation, the owner's admin profile and a one-workspace-per-person marker in one transaction, then sets the `{role: admin, orgId}` claims. A session cookie is only issued once the token carries a workspace. | Owners get a private workspace in one step, and a half-created account can never reach the app. |
| D59 | The workspace code (3 to 24 letters, digits, dashes; reserved words refused) is chosen by the owner or derived from the workspace name (acme, acme-2 …). Employees' Firebase Auth emails are `username@code.traxio.app`, so usernames only need to be unique inside a workspace. The code is not secret. | Short for people to type, valid as a hostname label, and two customers can both have an "ali". |
| D60 | Sign-up is a transaction with a per-person marker (`orgOwners/{uid}`), checked against the database rather than the possibly stale token. | Two simultaneous or repeated sign-ups can't create two workspaces and point the claims at the wrong one (found by a test). |
| D61 | A workspace is capped at 25 team members (`MAX_EMPLOYEES_PER_WORKSPACE`), counted including turned-off people. Businesses are not capped (they are written from the browser). | A simple abuse limit on the free tier; one constant to change when plans exist. |
| D62 | Cron routes loop over every workspace (`forEachOrg`), isolate failures per workspace, and report a count. The AI summary and automation settings are per workspace. | One broken customer never stops the others. |
| D63 | The default Gemini model is `gemini-3.5-flash` (override with AI_MODEL). Gemini 2.5 Flash is closed to new accounts, and Google's `gemini-flash-latest` alias took over 40 s in testing while 3.5 Flash answers in about 10 s. Both providers now give up after 60 s with a friendly message. | A summary should take seconds, and a stuck provider must never hold a scheduled job open. |
| D64 | `npm run deploy:firebase` publishes Firestore rules, database rules and indexes through the Admin SDK, because the CLI's pre-check needs a service-usage permission the app's service account doesn't have. Rules need no extra role; creating indexes needs Cloud Datastore Index Admin. Server queries avoid composite indexes where one filter can be applied in memory (approved leave now queries only `toDate >= today`). | Deploys work with just the credentials the app already has, and server jobs keep working before the indexes finish building. |
| D65 | Automatic expiry of old activity entries (Firestore TTL) needs billing, so on the free plan it is skipped with a warning; old entries simply stay (text only, and the feed shows the latest 100). It switches on by itself if the project ever moves to Blaze and `npm run deploy:firebase` is run. | Keeps the project on the free plan without breaking the deploy. |
